# AI-Assisted Data Reconciliation

A Python tool that reconciles messy item records between two systems. It uses plain code for the easy matches, an LLM only for the ambiguous ones, and sends real conflicts to a human instead of fixing them automatically.

**[See the demo](https://jiyaabhan.github.io/recon-tool/)**

## Why I built this

This summer I worked as a Technology Consulting Intern on a NetSuite implementation for a furniture manufacturer. Part of the job was a data migration: auditing four client source systems, reconciling conflicting records, and rebuilding everything into validated import files. Most of that work was manual. The same item would appear under slightly different names or codes in different files, and the hardest part was not the obvious mismatches but the near-matches that looked right and weren't.

This project rebuilds that workflow on synthetic data to answer one question: where does AI actually help in a reconciliation task, and where does it need a human checkpoint?

No client data is used. Everything in `data/` is generated by `generate_data.py`.

## The data

`generate_data.py` creates a clean item master of 100 items (`source_a.csv`, standing in for the ERP) and a messy legacy copy (`source_b.csv`) with problems planted on purpose, modeled on the kinds of issues I ran into during the real migration:

| Planted problem | What it looks like |
|---|---|
| Legacy codes | The old system used its own codes (e.g. `L4241`), so only the name can identify the item |
| Abbreviated names | "Frm Stl 12 mm" instead of "Steel Frame 12mm", "Glide Blk" instead of "Floor Glide Black" |
| Prefix variants | `POW-0012` instead of `POWDER-0012` |
| Swapped code | A row carries another real item's code but describes a different item |
| Cost conflicts | The two systems disagree on an item's cost by 20% or more |
| Work centre conflicts | The two systems disagree on which work centre an item goes through |
| Duplicate row | The same item appears twice in the legacy file |
| Phantom item | A legacy item that does not exist in the ERP at all |
| Missing item | An ERP item with no legacy row |

Because the problems are planted, there is an answer key (`answer_key.csv`), which means the tool's output can be scored instead of eyeballed.

## How it works

`reconcile.py` runs each legacy row through three stages and stops at the first one that gives a confident answer.

1. **Exact code match, verified by name.** If the code exists in the ERP, the tool still checks that the names agree and that no other item fits the name better. This is what catches the swapped code, which a naive code lookup would accept.
2. **Confident fuzzy name match.** If the best name match scores 90 or above and clearly beats the runner-up, it is accepted. The runner-up check matters because variants like "Black" and "Grey" versions of the same product can score almost identically.
3. **LLM review for ambiguous rows.** Anything left goes to an LLM along with the top five candidates. The model must return JSON with a match (or "none"), a confidence level, and a one-sentence reason. Only high and medium confidence answers are accepted; everything else goes to human review.

After matching, every matched pair is checked for cost and work centre conflicts, duplicates are flagged, and ERP items that nothing matched are listed. All of these go to `output/review_queue.csv`. The tool does not decide which system has the right cost, because that is a business decision, not a data one.

Every decision, including the model's reasoning, is written to `output/decision_log.csv`.

## Results

Scored against the answer key (`score.py`). The tool was run on two datasets: the one used while building it (seed 42), and a second dataset generated afterwards with a different seed (7) that the tool had never seen. The second run is the fairer test, since the thresholds were set while looking at the first.

| Metric | Seed 42, no AI | Seed 42, with AI | Held-out seed 7, no AI | Held-out seed 7, with AI |
|---|---|---|---|---|
| Rows matched correctly | 91 / 101 (90%) | 101 / 101 (100%) | 95 / 101 (94%) | 101 / 101 (100%) |
| Confident wrong matches | 3 | 0 | 0 | 0 |
| Rows left unmatched | 8 | 1 (the phantom item, correctly) | 7 | 1 (the phantom item, correctly) |
| Items sent to human review | 37 | 12 | 24 | 12 |
| Rows sent to the LLM | n/a | 34 | n/a | 36 |

On both datasets, the AI stage resolved every ambiguous row correctly and answered "none" for the phantom item rather than forcing a match. The code-only baseline failed on the same kind of row both times: heavily abbreviated names like "Glide 32 mm" or "SS Screw Lg", where the fuzzy score was too low to trust.

The review queue is where the difference is most practical. With the AI stage, it came out at exactly 12 items on both datasets, and every one of them was a real planted problem: 5 cost conflicts, 3 work centre conflicts, the duplicate pair, the phantom item, and the missing item. The baseline queue was two to three times longer, padded with rows it simply couldn't match and, on the first dataset, false conflicts. Those false conflicts come from wrong matches: if the tool pairs two different items, it then compares their costs and flags a disagreement that isn't real.

## Where the AI got it wrong, and what the results don't prove

The model made no wrong matches in either run, so the honest question is what that 100% does and doesn't mean.

**The confidence levels were well calibrated.** The model marked 4 matches as medium confidence on the first dataset and 5 on the second. All 9 were correct, but in every case its reason was the same: the match rested on the name alone, because the legacy code gave no corroboration. For example, it matched "Mesh Panel Std" to "Rope Mesh Panel Standard" but noted that the legacy name drops the word "Rope", so the material wasn't confirmed. That is exactly the situation where a human reviewer should be less certain too. This row is also one the baseline got confidently wrong.

**What the results don't prove:**

- *The data is synthetic, and I designed the mess.* The abbreviations (Blk, Std, Frm Stl, Pwdr) are the kind an LLM reads easily. Real legacy data has stranger problems: internal shorthand, typos, and fields that mean different things in different systems.
- *The test sets are small.* 101 rows each, with about 35 reaching the LLM. A 100% result on 35 decisions is encouraging, not conclusive.
- *LLM output can vary between runs.* I ran each dataset once with the AI stage. A production version would need repeated runs to measure consistency.
- *The held-out test used the same generator.* A new seed produces new items and new placements of the problems, but the same kinds of problems. It shows the thresholds weren't overfitted to one dataset, not that the tool handles every kind of mess.

## What I changed and why

The main change was testing on a held-out dataset. After the first run scored 100%, the obvious concern was that the thresholds had been tuned while looking at that data. Generating a second dataset with a new seed and rerunning everything unchanged showed the result held.

I also considered accepting only high-confidence LLM answers and sending medium ones to review. I kept medium because all 9 medium-confidence answers across both runs were correct, and sending them to review would have added 4 to 5 rows to a human's queue per run for no accuracy gain. On real data with less predictable abbreviations, I would start with high-only and loosen it once the model had a track record.

See `DECISIONS.md` for the full log.

## Design choices

- **The LLM only sees ambiguous rows.** Most matches are handled by deterministic code, which is faster, free, and easy to audit. The model is used where judgment is actually needed.
- **The model has to explain itself.** Requiring a reason with every answer makes its decisions reviewable instead of a black box.
- **Low confidence means human review, not a guess.** The tool is designed to fail toward a person looking at the row, not toward a silent error.
- **Conflicts are flagged, never auto-resolved.** The tool can tell that two systems disagree. It cannot know which one is right.

## How I used AI to build this

I designed the scenario and the planted problems based on my migration work, and used Claude as a coding assistant to help write the generator, pipeline, and scoring scripts. I ran every stage, checked the output against the answer key, and reviewed the model's reasoning in the decision log row by row rather than trusting the accuracy number alone.

## How to run

To view the demo page locally, run `python -m http.server` in the repo folder and open `localhost:8000`.

Requires Python 3.10+.

```
python -m venv venv
venv\Scripts\activate          # Windows (use source venv/bin/activate on Mac/Linux)
python -m pip install -r requirements.txt

python generate_data.py                            # create the synthetic data (default seed 7; e.g. python generate_data.py 42)
python reconcile.py --no-llm && python score.py --baseline   # baseline, no API key needed
```

To run the AI stage, set an Anthropic API key first:

```
$env:ANTHROPIC_API_KEY = "your-key"    # PowerShell
python reconcile.py && python score.py
```

The baseline runs without any API key. The saved results in `output/` show the AI run, so you can see what it did without running it yourself.

## Files

| File | What it does |
|---|---|
| `generate_data.py` | Creates the synthetic ERP data, the messy legacy copy, and the answer key |
| `reconcile.py` | The three-stage matching pipeline plus conflict checks |
| `score.py` | Scores the output against the answer key |
| `index.html` | The demo page (GitHub Pages): results, the model's reasoning, and the review queue, read straight from the CSVs |
| `data/`, `output/` | Held-out run (seed 7): input data, answer key, matches, review queue, and decision log |
| `data_seed42/`, `output_seed42/` | The same files from the first run (seed 42) |
| `DECISIONS.md` | Log of design changes and their effect |
